## Flash layout validation (512KB mirror)

A 512KB chip (29F400BB) often mirrors into `0x800000`–`0x900000`.

If addressable flash extends past the layout:

- **Yes** — compare 64 bytes at offset 0 with the same offset above the layout
- **No** — continue
- **Cancel** — abort

Different data means the layout is likely too small (29F800). A match supports a mirror. Chip size still comes from the layout choice. A 512KB image that is not a mirror: [issue #80](https://github.com/NefMoto/NefMotoOpenSource/issues/80).

A sequence error or reject on the optional mirror probes completes as `EndIsntHighest` and continues (`TryCompleteOptionalMirrorProbeAsEndIsntHighest`). A read does not checksum until one sector has been uploaded and exited: the probe leaves `RequestUpload` open, and checksums do not clear the programming flag until `RequestTransferExit`.

### Prompts during a programming session

Tester present is sent only from `SendReceiveThread`. `DisplayUserPrompt` via `Dispatcher.Invoke`, or a completion that `Invoke`s into a dialog, holds that thread. Past P3 max (5s) the ECU stops answering. Reconnect ident is the RAM kernel ([issue #128](https://github.com/NefMoto/NefMotoOpenSource/issues/128)).

Session prompts use `PostUserPrompt` / `BeginDisplayUserPrompt` (`Dispatcher.BeginInvoke`). `RequestUpload`, `RequestDownload`, and the layout probes keep the `ResponsesFinishedEvent` hook so a no-reply finishes the action. Otherwise the next ident is delivered to it. Tests: `Tests/BlockingUserPromptTests.cs`.

The first `TransferData` after a successful erase and `RequestDownload` can miss its echo with no mirror dialog (`0x800000`–`0x803FFF` on 29F400BB). Leave P4, `TransmitBytes`, and the echo timeout alone.

### Flash layout (BT vs BB)

Same density, different small-sector cluster. The user picks the XML. Bootmode matches `FC_GETSTATE` to `FlashDeviceId`. **Wrong Flash Layout** uses `BootLabel` and `OppositeBootLabel`.

`29F800BT` can program the first 15 × 64KB, then fail erasing `0x8F0000`–`0x8F7FFF` (`Flash write failed: selected top-boot (BT) layout, chip looks bottom-boot (BB).`). The dialog is OK only and the write aborts. Pick the opposite layout and write again with checksum skip. Entire-flash erase uses the current sector list.

Uniform 29F800 (16 × 64KB) is a different mismatch. In-session layout switch is not implemented ([issue #103](https://github.com/NefMoto/NefMotoOpenSource/issues/103)).

## Defaults

Slow init address **`0x01`**; fast init physical, using the [physical target fallback](#physical-target-fallback) ([issue #123](https://github.com/NefMoto/NefMotoOpenSource/issues/123)).

After a write the ECU is on the RAM kernel until a complete power cycle. Prefer slow init then too ([RAM kernel after write](#ram-kernel-after-write-this_is_the_ram_program)). Other flash images differ. Direct K-line is not in-car (cluster).

## Slow init timing (ISO 14230)

Handshake uses **W0–W5**, not the session **P1–P4** timers. **P4** is tester inter-byte spacing after connect (default 5–20 ms). The critical handshake window is **W4**.

| Timer | Window | Meaning |
| --- | --- | --- |
| W1 | 60–450 ms | After address, wait for ECU `0x55` |
| W2 | 5–20 ms | Sync to first key byte |
| W3 | 0–20 ms | Between key bytes |
| **W4** | **25–50 ms** | After last key byte: tester sends `~key`; then ECU sends address complement |
| W5 | ≥ 300 ms | Idle before retransmitting the address |

**W4 is a hard window.** Extra work before `Write(~key)` (UI logs, waiting W3Max for a third key byte) can push past 50 ms. The ECU then sends nothing; the tester logs `success=True, read=0` on the address complement. A loaded host or in-car K-line through the cluster misses that window.

`SendSlowInit` (`Communication/KWP2000Interface.cs`):

- Stop the key-byte poll once two bytes are in
- Wait **W4Min**, then `Write` — no `DisplayStatusMessage` in that interval
- Read the address complement with a 100 ms timeout (W4Max + USB margin)

Typical ME7 keys `EF 8F` → tester `0x70` → address complement (`0xFE` for `0x01`, `0xEE` for `0x11`).

**Address byte framing:** the ME7 5-baud receiver takes a start bit plus 8 bits and compares the whole byte with its address table; it does not check parity. The address goes out as 8N1 (bit 7 = 0). 7O1 sends `0x11` as `0x91`, which does not match the table. `0x01` is the same bits either way.

## Connect UI

One **Connect address** field; meaning depends on **Slow init / Fast init** on the connect tab:

| Connect method | Address | Address mode |
| --- | --- | --- |
| Slow init | 5-baud byte (`0x01` default, `0x11` direct KWP2000) | Ignored |
| Fast init | StartCommunication target | Physical / Functional |

**Slow init `0x01`:** KWP1281 first (ident blocks; firmware table keys `01 8A`, log `KB1=0x01 KB2=0x0A` — `8A` is `0A` plus the odd parity bit), then a second slow init @ **`0x01`**. The second init answers with KWP2000 keys `EF 8F` and complement `0xFE` (the KWP1281-then-KWP2000 handoff), so the internal retry @ **`0x11`** is not reached. About 10 s from Connect.

**Slow init `0x11`:** direct KWP2000 (keys `EF 8F`, complement `0xEE`), no KWP1281 step; about 5 s from Connect (2.6 s idle, 1.8 s address, then the handshake). Images whose address table starts KWP2000 at `0x01` have no `0x11` entry; their `0x01` is already direct KWP2000 ([ME7 K-line addresses](ME7-K-line-addresses.md)).

**Engine running:** the KWP1281-then-KWP2000 handoff on `0x01` is armed only with engine speed 0. With the engine running the second `0x01` answers KWP1281 again, and the tool falls through to the internal `0x11` retry (a third slow init, about 15 s). `0x11` has no engine-speed gate on that path.

**`0x11` after a second KWP1281 `0x01`:** on images with no handoff, that second `0x01` is already the KWP2000 session. Connect then starts a programming session at the baud selected on the connect bar, highest rate at or below that selection first, same list a flash read uses. The link does not stay at 10400, which is what lets the cluster drop off ([issue #127](https://github.com/NefMoto/NefMotoOpenSource/issues/127)). A selection of 10400 does not start that session. A second `0x01` that is already KWP2000, and a first init that is already KWP2000, stay at 10400 until a read or write.

Per-image address tables, fast-init filter groups, and firmware addresses: [ME7 K-line addresses](ME7-K-line-addresses.md).

### Which to use

`0x01` stays the default. It works on every image, it is the path on the RAM kernel after a write, and per the ME7Logger README it avoids cars where the cluster interferes with `0x11`. `0x11` halves connect time where the image has it.

Settings tab hides **Fast init address mode** when connect tab uses slow init.

Fast init is handled by **whatever kernel is running**. Comments in `KWP2000Interface.cs`:

- Functional **`0xFE`** — external **flash** handler
- Functional **`0x02`** — external **RAM** handler
- Physical **`0x01`** — images whose boot-sector address filter compares against `0x01`
- Physical **`0x11`** — the [fallback](#physical-target-fallback) sends it. Some images set the physical RAM byte to `0x11` when the low word of RAM `0xE048` matches an image constant ([ME7 K-line addresses](ME7-K-line-addresses.md))
- Functional **`0x10`** / **`0x33`** — the app does not send these

### Physical target fallback

Images whose physical byte is `0x10` drop a physical request unless the target matches that RAM byte (`0x11` when that image's RAM flag is set). Physical fast init uses one target per connection attempt: `0x10`, then the **Connect address**, then `0x01`, then `0x11`, without repeats. With the defaults (address `0x01`, 3 attempts) that is `0x10`, `0x01`, `0x11`. The status log shows the target each attempt uses. The 2.6 s idle before a retry counts the silent time since the unanswered request, so each dropped target costs about 2.7 s (2.0 s reply timeout plus the rest of the idle and the wake-up).

The filter keys on the header address mode. Physical (`0x8n`) compares the target with the physical RAM byte. Functional (`0xCn`) accepts the functional RAM byte or the physical byte. A one-address header (`0x4n`) compares with its own RAM byte. A header with no address (`0x0n`) is always accepted. Only StartCommunication is affected: it goes out with a 3-byte header because the default key byte 1 (`0x6B`) does not allow 1-byte headers. The reply keys `EF 8F` do, so every later request uses a 1-byte header that the filter does not check. The reply source byte comes from the physical RAM byte. Functional fast init is unchanged.

Slow init does not go through this filter for the 5-baud address byte. After slow init the session also uses 1-byte headers (keys `EF 8F`), so the slow init `0x01` / `0x11` notes above are unaffected.

## RAM kernel after write (`THIS_IS_THE_RAM_PROGRAM`)

Not a NefMoto string. After KWP programming starts, ME7 copies the programming kernel into external RAM (`0x380000`, 32KB) and runs from there. Ident then comes from that kernel (KWP1281 `KWP1281 connect info:` ASCII, and KWP2000 ident fields). Usual text: `THIS-IS-THE-RAM-PROGRAM` (hyphens vary). Logging, DTCs, and engine start are flash-firmware features; they stay broken until the ECU leaves that kernel. The string by itself is not a brick. A dialog held past P3 on the same power-on is another way to land on that ident, distinct from a finished write ([Prompts during a programming session](#prompts-during-a-programming-session)).

A successful write that erased a sector disconnects KWP (`A sector was erased. Disconnecting from ECU.`). That is **not** a power cycle. Ident `0x9C` `FlashInconsistent` is cleared on disconnect after a complete flash; RAM ident lasts until a real power cycle.

| State | Ident | Power | What to do |
| --- | --- | --- | --- |
| Leftover programming session | RAM | Same power-on, after write or abort | Expected. Do not treat as a failed write. |
| Fail-safe | RAM after a **complete** power cycle | Flash rejected | Retry KWP with **slow init**. Bootmode if KWP dies. |
| No KWP | — | Flash / kernel not running | Bootmode only. |

**Success:** complete power cycle before expecting flash ident / logging / start (ME7.5: all +12, including pin 121). Reconnect with **slow init** @ **`0x01`** while the ident is still the RAM kernel.

**Abort** (Wrong Flash Layout, sector fail, comm drop with resume): **do not** power cycle. Retry KWP on the same power-on. Fast init functional **`0xFE`** is the flash handler and may not answer while the RAM kernel is running. Leave the fast-init defaults alone for that kernel ([issue #106](https://github.com/NefMoto/NefMotoOpenSource/issues/106)).

## CH340 slow init

Slow init uses **per-bit `SetBreak` toggles** (~200 ms/bit, 8N1) in `SendSlowInitAddress_UsingBreak`. Fast init uses a **single** short break — different path.

Production flow: `Connect_SlowInit()` → CH340 KKL DTR pulse + line restore → break-toggle send → optional UART fallback if break send fails → `WaitForTransmitDrain` before line changes.

Use **Slow init timing log** in settings when comparing CH340 vs FTDI bit timing. Sync wait **`W1Max` 450 ms**.

A long tester frame (download `TransferData`, once P4 min is 0) is sent in 16-byte slices. The echo of each slice is read before the next slice, so the CH340 receive FIFO does not overrun. The pause is the echo of one slice, about 2 ms at 124800, and stays under the 20 ms inter-byte cap, so the slice size is the same at every baud. Short frames, reads, and FTDI stay a single write.

## Settings persistence

Connect-tab **slow/fast init**, **baud**, and **slow-init timing log** are saved in `preferences.json` next to the log. Address, timings, security, and **`NumConnectionAttempts`** are session-only (`KWP2000SettingsDefaults.cs`).

**Restore To Defaults** resets the settings tab only — not connect method or baud.

CH340 slow init is always on. First launch with no JSON does not copy leftover FastInit from hashed `user.config`.

## Bench checklist

- Adapter in dumb mode; K-line direct to ECU; stable power
- Slow init @ **`0x01`** (or **`0x11`** for direct KWP2000 where the image has it)
- Wait **≥ 2.6 s** between connect attempts
- After a write, ident may be `THIS-IS-THE-RAM-PROGRAM` until a **complete** power cycle; reconnect with slow init. After an abort, stay powered and retry.
- Failures: `%AppData%\Nefarious Motorsports\NefMoto VW Audi ME7 Flasher Logger\NefMoto.log`

## StartDiagnosticSession (firmware)

`0x81` is accepted. `0x85` (programming) is refused with NRC `0x22` when engine speed is not 0. `0x86` (development) is accepted with no engine-speed check. Anything else is NRC `0x12`.
