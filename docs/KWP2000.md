### Flash layout validation (512KB mirror)

Many ME7.5 ECUs use a **512KB** flash chip (29F400BB) but map it **mirrored** into a **1MB** address space (`0x00800000`–`0x00900000`). With the **29F400BB** layout, layout validation used to fail with *End address is not the end of flash memory* even though the layout is correct for the physical chip.

When addressable flash extends past the selected layout, NefMoto asks whether to check for a mirrored mapping before continuing:

- **Yes** — check for mirror (compare a 64-byte sample at the start of the layout with the same offset above it)
- **No** — continue with this layout without checking
- **Cancel** — abort

If the check finds different data, the layout is likely too small (use **29F800**). A matching sample is strong evidence of mirroring, not absolute proof of chip size.

Example: `06A 906 032 CL` (2001 Golf/Jetta 1.8T AWD, narrowband / 512KB) — [issue #80](https://github.com/NefMoto/NefMotoOpenSource/issues/80).

### Prompts during a programming session

Tester present is sent only from `SendReceiveThread`. A modal `DisplayUserPrompt` (`Dispatcher.Invoke`), or a completion handler that `Dispatcher.Invoke`s and then shows a dialog, holds that thread. Past P3 max (5s on the field ECU) the ECU stops answering. Reconnect ident is the RAM kernel ([issue #128](https://github.com/NefMoto/NefMotoOpenSource/issues/128)).

KWP operation prompts go through `PostUserPrompt` / `BeginDisplayUserPrompt`. UI completions that show a dialog use `Dispatcher.BeginInvoke`. `RequestUpload`, `RequestDownload`, and the layout probes must keep the `ResponsesFinishedEvent` hook. A no-reply otherwise never finishes the action, and the next ident can be delivered to it.

The regression check is `Tests/BlockingUserPromptTests.cs`. The post-erase `TransferData` silence is a different failure. Do not change P4 or `TransmitBytes` from this note.

### Flash layout (BT vs BB)

29F800 / 29F400 / 29F200 exist as **top-boot (BT)** and **bottom-boot (BB)**. Same density, different small-sector cluster. KWP has no flash device ID; the user picks the XML. Bootmode reads `FC_GETSTATE` and selects the file whose `FlashDeviceId` matches. `BootLabel` and `OppositeBootLabel` are the words in **Wrong Flash Layout**.

These bench 29F800 units are **BB** (`29F800BB`). A KWP write with `29F800BT` can program the first 15 × 64KB (legal unions on BB), then fail erasing `0x8F0000`–`0x8F7FFF`. Status is one line (`Flash write failed: selected top-boot (BT) layout, chip looks bottom-boot (BB).`). Dialog **Wrong Flash Layout** (OK only); the write aborts. Recovery: pick the named opposite layout and write again with checksum skip. Entire-flash erase still uses the current sector list and does not fix BT vs BB.

The same erase NRC used to open **Sector Erase Failed** (persistent data). Uniform `29F800` (16 × 64KB) is a different mismatch. Switching layout in the same programming session is not implemented ([issue #103](https://github.com/NefMoto/NefMotoOpenSource/issues/103)).

## Results (defaults)

Slow init address **`0x01`**; fast init physical, using the [physical target fallback](#physical-target-fallback) ([issue #123](https://github.com/NefMoto/NefMotoOpenSource/issues/123)). ME7.1 FTDI fast init has not been retested since the fallback.

| ECU | Adapter | Slow init | Fast init |
| --- | --- | --- | --- |
| ME7.1 | FTDI | ✅ | ✅ |
| ME7.1 | CH340 | ✅ | ✅ |
| ME7.5 | FTDI | ✅ | ✅ |
| ME7.5 | CH340 | ✅ | ✅ |

ME7.5 fast init (`4B0906018CH` unit, `0261208164`, running `06A906032NL`) connects at `0x10` on the first attempt with both adapters. Before the fallback it failed, because the boot-sector address filter dropped `81 01 F1 81`. ME7.1 fast init (`8D0907551M` 0002, CH340) gets no reply at `0x10` and connects at `0x01` on the second attempt, about 5.5 s after Connect. Ident, DTC and memory reads work after connect on both.

**Bench guidance:** slow init @ **`0x01`** and fast init both work. After a write the ECU is on the RAM kernel until a complete power cycle — prefer slow init then too ([RAM kernel after write](#ram-kernel-after-write-this_is_the_ram_program)). Other flash images may differ.

Direct K-line is not in-car (cluster).

## Slow init timing (ISO 14230)

Handshake uses **W0–W5**, not the session **P1–P4** timers. **P4** is tester inter-byte spacing after connect (default 5–20 ms). The critical handshake window is **W4**.

| Timer | Window | Meaning |
| --- | --- | --- |
| W1 | 60–450 ms | After address, wait for ECU `0x55` |
| W2 | 5–20 ms | Sync to first key byte |
| W3 | 0–20 ms | Between key bytes |
| **W4** | **25–50 ms** | After last key byte: tester sends `~key`; then ECU sends address complement |
| W5 | ≥ 300 ms | Idle before retransmitting the address |

**W4 is a hard window.** Extra work before `Write(~key)` (UI logs, waiting W3Max for a third key byte) can push past 50 ms. The ECU then sends nothing; the tester logs `success=True, read=0` on the address complement. Idle bench often still hits `0xFE`; a loaded host or in-car K-line through the cluster may not.

`SendSlowInit` (`Communication/KWP2000Interface.cs`):

- Stop the key-byte poll once two bytes are in
- Wait **W4Min**, then `Write` — no `DisplayStatusMessage` in that interval
- Read the address complement with a 100 ms timeout (W4Max + USB margin)

Typical ME7 keys `EF 8F` → tester `0x70` → address complement (`0xFE` for `0x01`, `0xEE` for `0x11`).

**Address byte framing:** the ME7 5-baud receiver (`8D0907551M` `0x82B6DA`) takes a start bit plus 8 bits and compares the whole byte with its address table; it does not check parity. The address therefore goes out as 8N1 (bit 7 = 0). With 7O1, `0x11` went out as `0x91` and never matched; 7E1 (the old internal retry) happened to send `0x11`. `0x01` is the same bits either way.

## Connect UI

One **Connect address** field; meaning depends on **Slow init / Fast init** on the connect tab:

| Connect method | Address | Address mode |
| --- | --- | --- |
| Slow init | 5-baud byte (`0x01` default, `0x11` direct KWP2000) | Ignored |
| Fast init | StartCommunication target | Physical / Functional |

**Slow init `0x01`:** KWP1281 first (ident blocks; firmware table keys `01 8A`, log `KB1=0x01 KB2=0x0A` — `8A` is `0A` plus the odd parity bit), then a second slow init @ **`0x01`**. On both bench units the second one answers with KWP2000 keys `EF 8F` and complement `0xFE` (the firmware's KWP1281-then-KWP2000 handoff), so the internal retry @ **`0x11`** is not reached. About 10 s from Connect.

**Slow init `0x11`:** direct KWP2000 (keys `EF 8F`, complement `0xEE`), no KWP1281 step; about 5 s from Connect (2.6 s idle, 1.8 s address, then the handshake). Works on both bench units with FTDI and CH340. Images whose address table starts KWP2000 at `0x01` (`8E0909518`, `4B0906018DQ`, and the other images in groups E–F of [ME7 K-line addresses](ME7-K-line-addresses.md)) have no `0x11` entry; their `0x01` is already direct KWP2000.

**Engine running (static analysis, not bench-tested):** the KWP1281-then-KWP2000 handoff on `0x01` is only armed with engine speed 0 (`8D0907551M` `0x8652C4`, `0x86441E`, `0x82B8B8`). With the engine running the second `0x01` should answer KWP1281 again, and the tool falls through to the internal `0x11` retry (a third slow init, about 15 s). `0x11` has no engine-speed gate on that path.

Per-image address tables, fast-init filter groups, and firmware addresses: [ME7 K-line addresses](ME7-K-line-addresses.md).

**Which to use:** `0x01` stays the default: it works on every image, is the tested path on the RAM kernel after a write, and per the ME7Logger README avoids cars where the cluster interferes with `0x11`. `0x11` halves connect time where the image has it.

Settings tab hides **Fast init address mode** when connect tab uses slow init.

Fast init is handled by **whatever kernel is running**. Comments in `KWP2000Interface.cs`:

- Functional **`0xFE`** — external **flash** handler (YES on bench)
- Functional **`0x02`** — external **RAM** handler (UNTESTED)
- Physical **`0x01`** — YES on images whose boot-sector address filter compares against `0x01`
- Physical **`0x11`** — the [fallback](#physical-target-fallback) sends it. Bench units gave no reply. Some images set the physical RAM byte to `0x11` when the low word of RAM `0xE048` matches an image constant ([ME7 K-line addresses](ME7-K-line-addresses.md))
- Functional **`0x10`** / **`0x33`** — NO on bench

### Physical target fallback

Images with a `0x10` filter (`06A906032NL`, the `4B0906018CH` family, `8E0909518`, about half of the surveyed set) drop a physical request unless the target matches a RAM byte, normally `0x10` (`0x11` when that image's RAM flag is set). Physical fast init therefore uses one target per connection attempt: `0x10`, then the **Connect address**, then `0x01`, then `0x11`, without repeats. With the defaults (address `0x01`, 3 attempts) that is `0x10`, `0x01`, `0x11`. The status log shows the target each attempt uses. The 2.6 s idle before a retry counts the silent time since the unanswered request, so each dropped target costs about 2.7 s (2.0 s reply timeout plus the rest of the idle and the wake-up).

On `06A906032NL` the filter (`0x839BCA` → boot `0x002C1A`, image `0x802C1A`) keys on the header address mode. Physical (`0x8n`) compares the target with `0xE20A`. Functional (`0xCn`) accepts `0xE20B` or `0xE20A`. `0x4n` compares with `0xE20D`. A header with no address (`0x0n`) is always accepted. Only StartCommunication is affected: it goes out with a 3-byte header because the default key byte 1 (`0x6B`) does not allow 1-byte headers. The reply keys `EF 8F` do, so every later request uses a 1-byte header that the filter does not check. The reply's source byte also comes from `0xE20A` (builder `0x8396FA`, boot copy `0x002D28`, image `0x802D28`). Functional fast init is unchanged.

Slow init does not go through this filter for the 5-baud address byte. After slow init the session also uses 1-byte headers (keys `EF 8F`), so the slow init `0x01` / `0x11` notes above are unaffected.

## RAM kernel after write (`THIS_IS_THE_RAM_PROGRAM`)

Not a NefMoto string. After KWP programming starts, ME7 copies the programming kernel into external RAM (`0x380000`, 32KB) and runs from there. Ident then comes from that kernel (KWP1281 `KWP1281 connect info:` ASCII, and KWP2000 ident fields). Usual text: `THIS-IS-THE-RAM-PROGRAM` (hyphens vary). Logging, DTCs, and engine start are flash-firmware features; they stay broken until the ECU leaves that kernel. The string by itself is not a brick. A dialog held past P3 on the same power-on is another way to land on that ident, distinct from a finished write ([Prompts during a programming session](#prompts-during-a-programming-session)).

A successful write that erased a sector disconnects KWP (`A sector was erased. Disconnecting from ECU.`). That is **not** a power cycle. Ident `0x9C` `FlashInconsistent` is cleared on disconnect after a complete flash; RAM ident lasts until a real power cycle.

| State | Ident | Power | What to do |
| --- | --- | --- | --- |
| Leftover programming session | RAM | Same power-on, after write or abort | Expected. Do not treat as a failed write. |
| Fail-safe | RAM after a **complete** power cycle | Flash rejected | Retry KWP with **slow init**. Bootmode if KWP dies. |
| No KWP | — | Flash / kernel not running | Bootmode only. |

**Success:** complete power cycle before expecting flash ident / logging / start (ME7.5: all +12, including pin 121). Reconnect with **slow init** @ **`0x01`** if still talking to the RAM kernel (`0x11` is untested on the RAM kernel).

**Abort** (Wrong Flash Layout, sector fail, comm drop with resume): **do not** power cycle. Retry KWP on the same power-on. Fast init functional **`0xFE`** is the flash handler and may not answer while the RAM kernel is running. Functional **`0x02`** is untested; do not change defaults until a RAM-kernel matrix exists ([issue #106](https://github.com/NefMoto/NefMotoOpenSource/issues/106)).

## CH340 slow init

Slow init uses **per-bit `SetBreak` toggles** (~200 ms/bit, 8N1) in `SendSlowInitAddress_UsingBreak`. Fast init uses a **single** short break — different path.

Production flow: `Connect_SlowInit()` → CH340 KKL DTR pulse + line restore → break-toggle send → optional UART fallback if break send fails → `WaitForTransmitDrain` before line changes.

Use **Slow init timing log** in settings when comparing CH340 vs FTDI bit timing. Sync wait **`W1Max` 450 ms** (ECU `0x55` ~301 ms after address on ME7.1 FTDI bench).

## Settings persistence

Connect-tab **slow/fast init**, **baud**, and **slow-init timing log** are saved in `preferences.json` next to the log. Address, timings, security, and **`NumConnectionAttempts`** are session-only (`KWP2000SettingsDefaults.cs`).

**Restore To Defaults** resets the settings tab only — not connect method or baud.

CH340 slow init is always on. First launch with no JSON does not copy leftover FastInit from hashed `user.config`.

## Bench checklist

- Adapter in dumb mode; K-line direct to ECU; stable power
- Slow init @ **`0x01`** (or **`0x11`** for direct KWP2000 where the image has it)
- Wait **≥ 2.6 s** between connect attempts
- After a write, ident may be `THIS-IS-THE-RAM-PROGRAM` until a **complete** power cycle; reconnect with slow init. After an abort, stay powered and retry.
- Failures: `%AppData%\Nefarious Motorsports\NefMoto VW Audi ME7 Flasher Logger\NefMoto.log`
