# P1681 and P0602

Bit 7 of byte 8 on 95040 pages 30 and 31 is the EEPROM flag. The byte follows the six-byte tool-code field. Both copies match. What to do when `P0602` is set is in [P0602](user-guide/clearing-P0602.md).

A key cycle with the flag set stores `P0602` on software that has this path. Customer code is `0x0602`. CARB code is `0x1681`. This tool reads DTCs with service `0x18`, status `0x00`, group `0x0000`, which returns the customer code, so the list shows `P0602`. Software with no fault test for the bit leaves `P0602` off the list while the flag is set.

A late B-chassis image written onto the older A-chassis ECU leaves KWP silent. Bootmode still answers. Do not do that write.

## Kernel

The programming kernel runs from the image when the session starts. It is copied to RAM at `0x380000`.

- **Login sets the flag.** A correct key for seed `0x01` sets bit 7 of byte 8, advances the first counter (byte 9), and writes both pages. A seed request at level 3 skips that step for the rest of the session. This tool asks for seed `0x01`.
- **Three matching checksums clear it.** While `33 C5` runs it answers `7F 33 23`. A match answers `73 C5 00` and adds one to a streak. A mismatch answers `7F 33 77` and resets the streak. On the third match the streak resets. If the flash sum passes, byte 8 is zeroed, the second counter (byte 10) advances, and both pages are written. The flash sum ignores the tester's range.
- **An open upload stops the count.** An accepted `0x35` sets a latch before the upload starts. Only a finished upload followed by a successful `0x37` clears it. While the latch is set, `33 C5` results are neither counted nor reset.

`ValidateStartAndEndAddressesWithRequestUploadDownloadAction` runs first in every KWP read and write. It sends `0x35` probes and never sends TransferData or `0x37`. A diff read or a full read uploads a sector and exits, which clears the latch. A write downloads only, so a write ends with a 2-byte upload and exit.

On a KWP layout whose sector 0 is 16 KB at `0x800000`:

- **Diff Read Flash** uploads sector 0, checksums it, then checksums the remaining sectors. The flag ends clear.
- **Diff Write Flash** checksums each sector, writes the ones that differ, then uses the same closing step as a full write. The flag ends clear.
- **Full Read Flash** uploads every sector. **Verify Read** checksums every sector after its upload. Unchecked, on a bottom-boot layout with at least four sectors, the read checksums the first four and uploads the rest with no checksum. A bootmode read sends no `0xC5`. A read on a layout whose sector 0 is some other size or address also sends no `0xC5`.
- **Full Write Flash**, after the last sector, uploads 2 bytes at the start of flash (`0x800000`), exits, and checksums the first finished sector three times. The flag ends clear.
- **Check if Flash Matches** logs in and checksums each sector of the loaded file, with no upload. Three matching sectors in a row clear the flag.
- A read that fails after at least one sector finished ends with the same closing step, using the first sector that finished. **Cancel Current Operation** waits for the current request and then does the same. A second cancel stops at once and leaves the flag set. A read that fails before any sector finished, and a write that stops partway, end with the flag set.

A correct key that is not followed by three counted matches leaves byte 8 at `0x80`. That includes a checksum with an open upload, a full read that sends no checksum, and a write that stops before the closing step.

## Clearing

**Clear DTCs** offers three checksums of sectors 1, 2, and 3 when the last read contained `P0602` or `P1681` and either bit 7 is set or the mirror page at `0x6001E0` cannot be read. A checksum mismatch names the loaded file, reads those three sectors from the ECU, and checksums the bytes just read. If the ECU stops answering before a checksum comes back, the file is not named and those sectors are not read.

The kernel does not care which ranges match. The third match in a row, with no open upload, clears the flag. The three calls are:

```text
31 C5 80 40 00 80 5F FF XX XX
33 C5

31 C5 80 60 00 80 7F FF XX XX
33 C5

31 C5 80 80 00 80 FF FF XX XX
33 C5
```

`XX XX` is the checksum of that sector in the loaded file. One checksum of `0x800000`–`0x80FFFF` is a single match and leaves the flag set.

A `Debug` build adds one row on the Flashing tab: **Check if Flash Matches** and **Checksum 8K+8K+32K**. A release build does not show it. **Check if Flash Matches** lists sectors that differ and saves nothing. It is disabled in bootmode. **Checksum 8K+8K+32K** runs the three calls above, and only when sector 0 is 16 KB at `0x800000`. Stock software that never stores `P0602` from this bit does not offer the checksum from **Clear DTCs**, and the debug button is the manual clear.

The programming session rejects `ReadMemoryByAddress` at `0x6001E0`. The mirror read logs in, opens a development session, and sends `23 60 01 E0 10`. A rejected login does not abort.

## The store in the flash file

Some images decide whether to store `P0602` from this flag with one instruction. The signature is `DB 00 28 02 84 00 ?? ?? C2 F4 ?? ?? 66 F4 80 00 2D`. The `2D` is `JMPR cc_Z` (jump if zero). The next byte is the displacement. Changing `2D` to `0D` (`JMPR cc_UC`, jump always) skips the bit-field update and still reaches the call. The displacement byte stays. This tool does not apply that change. The image still needs its checksums corrected.

The instruction tests the RAM copy of EEPROM byte 8. One path stores marker `0xA5F0` (fault) and the other stores `0x5A0F` (clear). The customer codeword for this path is `0x0602`. The CARB codeword is `0x1681`.
